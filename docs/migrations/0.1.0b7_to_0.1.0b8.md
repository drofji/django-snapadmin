# Migrating: 0.1.0b7 → 0.1.0b8

There is **no database migration** in this release. The items below are dependency / settings
changes. The full notes are in [`docs/releases/0.1.0b8.txt`](../releases/0.1.0b8.txt); this guide
covers only the steps you must take.

## 1. `djangorestframework`, `drf-spectacular`, `django-filter` and `graphene-django` are now optional extras (BREAKING)

They moved out of the core dependency list into two extras: `[api]` (djangorestframework,
drf-spectacular, django-filter) and `[graphql]` (graphene-django, independent of `[api]`). A bare
`pip install django-snapadmin` no longer pulls any of the four.

**Who is affected:** anyone whose install relies on `pip install django-snapadmin` alone to provide
the REST API and/or GraphQL — which is most installs, since neither surface had to be asked for
before this release. Note that this release *also* flips `SNAPADMIN_REST_API_ENABLED` and
`SNAPADMIN_GRAPHQL_ENABLED` to default to `False` ([step 2](#2-snapadmin_rest_api_enabled--snapadmin_graphql_enabled-now-default-to-false-breaking)),
so keeping either surface takes **both** changes: the extra from this step *and* the setting from
that one. Installing the extra alone leaves the surface off. An admin-only install that already runs
with both settings set to `False` is unaffected by either change.

**Action — pick the extras matching what you use:**

```bash
# REST API + Swagger/ReDoc only
pip install django-snapadmin[api]

# GraphQL only
pip install django-snapadmin[graphql]

# Both (equivalent to today's default dependency graph, minus the settings default flip below)
pip install django-snapadmin[api,graphql]

# Every extra the package offers — a no-op upgrade for an install that already has everything
pip install django-snapadmin[all]
```

If you pin dependencies (a lockfile, a `requirements.txt` that lists `django-snapadmin` without
extras), add the extra there rather than installing it ad hoc, or the next `pip install -r
requirements.txt` on a clean environment silently drops the REST API and/or GraphQL again.

Leaving a feature enabled with its extra missing is not silent: `snapadmin.urls` raises
`ImproperlyConfigured` naming the extra to install (or the setting to turn off) the moment the
URLconf is imported, and `manage.py check` catches it earlier still (`snapadmin.E010`).

## 2. `SNAPADMIN_REST_API_ENABLED` / `SNAPADMIN_GRAPHQL_ENABLED` now default to `False` (BREAKING)

Both settings flip their built-in default at this release — see the `Breaking` entry in
[`docs/releases/0.1.0b8.txt`](../releases/0.1.0b8.txt) for the full rationale and the deprecation
warning (`snapadmin.W014`) that announced this in an earlier beta.

**Action:** if you rely on either surface and have never set the setting explicitly, set it now:

```python
SNAPADMIN_REST_API_ENABLED = True
SNAPADMIN_GRAPHQL_ENABLED = True
```

Combine this with step 1 above — the setting being `True` with the matching extra installed is what
today's behaviour actually was.

## 3. The deprecated command aliases and underscored console scripts are removed (BREAKING)

This release closes the beta-series removal window announced across several `0.1.0b` releases and
in `SECURITY.md`'s API-stability policy. Nothing below is new — it has been flagged since
`0.1.0b6` — but it now actually takes effect:

| Removed name | Use instead |
|---|---|
| `db_backup` (management command) | `snapadmin_db_backup` |
| `purge_expired_data` (management command) | `snapadmin_purge_expired_data` |
| `send_error_digest` (management command) | `snapadmin_send_error_digest` |
| `snapadmin_info` (underscored console script) | `snapadmin-info` (or `manage.py snapadmin_info`) |
| `snapadmin_license_check` (underscored console script) | `snapadmin-license-check` (or `manage.py snapadmin_license_check`) |

**Action:** update any crontab, Celery Beat entry, deploy script or shell alias that still calls one
of the removed names on the left before upgrading — there is no runtime fallback and no deprecation
warning left to catch it after this release.

## 4. `SNAPADMIN_PROFILE = "full"` / `"api"` now really mount REST, GraphQL and Swagger (BREAKING)

If you set `SNAPADMIN_PROFILE` to `"full"` or `"api"`, this release changes what it does: both
presets now resolve `SNAPADMIN_REST_API_ENABLED`, `SNAPADMIN_GRAPHQL_ENABLED` and
`SNAPADMIN_SWAGGER_ENABLED` to `True` explicitly, matching what the profile has always been
documented to mean. See the `Breaking` entry in
[`docs/releases/0.1.0b8.txt`](../releases/0.1.0b8.txt) for the full detail — in short, before this
release both presets were empty and silently fell through to the (now `False`) built-in defaults
from step 2, so `SNAPADMIN_PROFILE = "full"` was quietly running admin-only.

**Action:** if you carry `SNAPADMIN_PROFILE = "full"` or `"api"`, audit your write allowlists
(`api_write_fields`) and PII masking before upgrading — the API surface is about to actually turn
on. Pin `SNAPADMIN_REST_API_ENABLED = False` / `SNAPADMIN_GRAPHQL_ENABLED = False` explicitly (an
explicit setting always wins over a profile), or drop `SNAPADMIN_PROFILE` entirely, to keep
admin-only behaviour.

## 5. `manage.py check` may now report `snapadmin.W015` — an empty change form

New in this release, and the only item here that is not a breaking change: `snapadmin.W015` warns
when a registered model's **generated** change form would render with no fields at all. Nothing
about your project changed — the warning did not exist in `0.1.0b7`, so a model that has always
produced an empty form only now says so.

The cause is `show_in_form`, which decides whether a field appears on the add/change form and
defaults to **`False`**. `show_in_list` defaults to `True`, so such a model has a perfectly normal
changelist and an empty form, which is why it can go unnoticed for a long time.

**Action — only if the warning names one of your models:**

```python
# Per field: name the fields that belong on the form.
name = snap_fields.SnapCharField(max_length=200, show_in_form=True)
```

```python
# Or project-wide, new in this release, for a codebase that never set the flag anywhere:
SNAPADMIN_SHOW_IN_FORM_DEFAULT = True    # only changes what an *unset* field resolves to
```

An explicit per-field `show_in_form=` still wins over the setting, so raise the default and then
switch off the fields that should not be editable. A model you registered yourself with a
hand-written `ModelAdmin` is never reported — that form owes nothing to `show_in_form`.

## Not a migration, but worth knowing

- **`nh3` stays a core dependency.** It was evaluated for the same treatment as the four packages
  above and kept in core: HTML sanitization is a security control, and a missing `nh3` on a normal
  install must not be a state a security-relevant default can silently reach. It is MIT and tiny.
- **The base install is now three packages: Django, structlog, nh3.** Every other integration
  SnapAdmin offers — REST, GraphQL, the Unfold theme, Elasticsearch, Celery, the backup transports,
  wysiwyg, XLSX export — was already, or is now, an explicit opt-in extra.
- **`SnapModel.get_admin_fields()` now returns an `AdminFieldSets` named tuple.** The members are
  `(form_fields, list_display, search_fields, list_filter, autocomplete_fields)` — the same five
  values in the same order as before, so positional unpacking, indexing and `len()` all keep
  working untouched and no upgrade step is needed. What changes is that the members can be read by
  name (`MyModel.get_admin_fields().autocomplete_fields`), and that the shape is now pinned: a
  future sixth member would be an announced breaking change rather than a `ValueError` discovered
  at admin autodiscovery. Only relevant if your project calls the classmethod itself, from a custom
  `register_admin()` or an admin that reuses the generated field lists.
