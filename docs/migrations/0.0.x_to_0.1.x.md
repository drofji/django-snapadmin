# Migrating: v0.0.x → v0.1.x

Version 0.1.0 is a significant rewrite. If you are upgrading from an older version, follow these steps.

## 1. Update the package

```bash
pip install --upgrade django-snapadmin
```

## 2. Replace model field imports

```python
# Before (v0.0.x)
from snapadmin.fields import CharField, IntegerField  # bare re-exports

# After (v0.1.x)
from snapadmin import fields as snap
name = snap.SnapCharField(max_length=200, searchable=True, show_in_list=True)
```

## 3. Update SnapModel usage

```python
# Before (v0.0.x)
from snapadmin.models import BaseModel
class Product(BaseModel): ...

# After (v0.1.x)
from snapadmin.models import SnapModel
class Product(SnapModel): ...
```

## 4. Admin registration

```python
# After (v0.1.x) — add to your app's admin.py:
from snapadmin.models import SnapModel
SnapModel.register_all_admins()  # registers all SnapModel subclasses
```

## 5. New settings

```python
# settings.py additions for v0.1.x:
SNAPADMIN_REST_API_ENABLED = True    # off unless set — needs the [api] extra
SNAPADMIN_GRAPHQL_ENABLED  = True    # off unless set — needs the [graphql] extra
SNAPADMIN_SWAGGER_ENABLED  = True    # follows SNAPADMIN_REST_API_ENABLED unless set
ELASTICSEARCH_ENABLED      = False   # default False — enable only with ES cluster
SNAPADMIN_ES_QUERY_ROUTING = True    # default True — ?search= on DUAL models → ES
SNAPADMIN_ES_SEARCH_LIMIT  = 1000    # default 1000 — max ES hits per routed search
```

> **The REST and GraphQL surfaces are opt-in.** Both switches default to `False`, and the packages
> behind them are optional extras — `pip install django-snapadmin[api,graphql]`. Including
> `snapadmin.urls` on its own mounts the admin and nothing else; the two lines above are what turn
> the API on, not documentation of what you already have. Turning a surface on without its extra
> fails loudly at `manage.py check` (`snapadmin.E010`) rather than silently. `SNAPADMIN_SWAGGER_ENABLED`
> has no default of its own — it follows whatever `SNAPADMIN_REST_API_ENABLED` resolved to, so
> Swagger never documents a REST surface that is not mounted.

> **No data migration needed.** SnapAdmin does not add columns or constraints to your existing model
> tables. The only new table is `snapadmin_apitoken` (for the token auth feature). Run
> `python manage.py migrate` after upgrading.

> **Expect an `AlterField`-only migration.** Every `Snap*Field` records its own dotted class path
> in `deconstruct()` (`snapadmin.fields.SnapCharField`, not Django's `CharField`), so the moment
> step 2 changes a model's fields, Django's autodetector sees every converted field as changed —
> even though the column itself is identical, because the Snap-only kwargs
> (`searchable`, `show_in_list`, …) never reach `deconstruct()`. The first `makemigrations` after
> the swap therefore produces a migration that is nothing but `AlterField` operations, one per
> converted field; a wide model can produce well over a hundred of them.
>
> **This is expected, not a bug.** On PostgreSQL and MySQL an `AlterField` that changes only a
> field's *Python* class — not its SQL type, nullability or default — is a no-op at the database
> level. **On SQLite it rebuilds the table** (SQLite has no native `ALTER COLUMN`, so Django
> recreates the table and copies every row): slower on a large table, but data-preserving. Review
> it before applying in production, as with any migration:
>
> ```bash
> python manage.py makemigrations yourapp   # produces N × AlterField, nothing else
> python manage.py sqlmigrate yourapp 000X  # confirm: no column type/constraint actually changes
> ```
